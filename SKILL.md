# Chief of Staff

The chief uses a highly capable model to plan, delegate, and review from the main checkout. Defaults: `openai/gpt-6-astra` with medium reasoning for the chief, and `openai/gpt-6.1-sol` with medium reasoning for workers. Verify these exact model IDs in the installed catalog; honor user overrides. If a default is unavailable, report it and ask for a replacement rather than silently substituting another version. Verify the chief's model instead of claiming it changed; use the session's model selector when needed.

1. **Prepare.** Load the `herdr` and `pi-intercom` skills and read [the coordination protocol](references/intercom-coordination.md). Require `HERDR_ENV=1` and the `wt` CLI. If the Herdr skill is not installed, load it with `herdr --skill`. Inspect `wt hook show`, `wt list`, `herdr status`, `herdr workspace list`, `herdr worktree`, and `herdr agent list`; call `intercom({ action: "status" })` and `intercom({ action: "list" })`. Check `pi --help` and resolve models with `pi --list-models`. The roster only includes sessions with pi-intercom loaded and connected; it is not every Herdr agent. After a resume or CLI update, reconcile live sessions, pending asks, and worktrees before restarting anything; resume the existing worker where possible.
2. **Assess risk first.** Before creating tasks or launching agents, assess the complete proposed change and record each assignment’s risk and reason. Low risk means limited impact and easy reversal. High risk includes access controls, payments, sensitive data, destructive changes, migrations, production releases, broad impact, or uncertain consequences. Reassess when scope or risks change.
3. **Isolate.** Create each task’s worktree with `command wt -C <repo> switch --create <branch> --no-cd --format=json`. Read its path and record the starting commit as `<base>` before any edits. Worktrunk owns creation and removal. Use its setup hooks and verify readiness, including background setup; otherwise use the repository’s documented setup.
4. **Launch and register.** Default to Pi workers so both chief and workers can use pi-intercom. For every worker (including explicitly requested non-Pi workers), open the Worktrunk-created worktree with `herdr worktree open --workspace <chief-workspace-id> --path <path> --label "<task>" --no-focus`, then `herdr agent start <name> --kind pi --pane <pane> -- --name <task-session-name> --model <provider/model> --thinking medium`. Set the worker model explicitly and use a unique Pi session name. Resolve `<chief-workspace-id>` from the caller context and live workspace list, never the UI-focused workspace. `worktree open` registers repository/worktree metadata so Spaces groups the worker under the repository's main workspace; this is workspace grouping, not an intercom or agent parent-child relationship. Do not use plain `workspace create`, intercom auto-creation, or `herdr worktree create` for workers: Worktrunk still owns worktree creation. Read workspace/pane IDs from `.result.workspace` and `.result.root_pane` in the open response. If it reports `already_open`, inspect and reuse the existing workspace/worker; never start over an occupied pane. Before starting a new worker, verify with `herdr workspace list` and `herdr worktree list --workspace <chief-workspace-id>` that the main workspace and worker have the same `worktree.repo_key`, the worker has `is_linked_worktree: true`, and its checkout path matches `<path>`. If the main workspace lacks metadata, inspect `herdr worktree open --help` and register/reuse the main checkout with `herdr worktree open --cwd <repo> --path <repo> --no-focus`; re-discover IDs and verify grouping. If the installed CLI/server cannot register this grouping, stop and report the blocker rather than silently creating a flat workspace or upgrading/restarting Herdr. Then discover the worker with `intercom({ action: "list-cwd", cwd: "<path>" })`; verify its directory and model before sending work. Track task, risk, model, branch, base, path, workspace, Herdr agent/pane, chief intercom ID, worker intercom ID, and message IDs. Herdr agent names, pane IDs, and Pi intercom IDs are distinct; never derive one from another. If registration fails, inspect startup and connectivity rather than creating duplicate workers. Honor an explicit non-Pi worker request using the fallback protocol.
5. **Delegate a detailed plan.** Provide the goal, scope, ordered implementation steps, files to inspect or change, key decisions, repository rules, risk and reason, acceptance criteria, exact verification commands, and required deliverable. Send the initial plan through `intercom({ action: "send", to: "<worker-id>", cwd: "<path>", message: "<plan>" })`. Include the chief’s exact intercom ID, task ID, and reporting protocol: acknowledge receipt, use `send` for milestones and completion, and `ask` only when blocked on a chief decision. Workers report ambiguity or plan failures to the chief for revised instructions; do not expand scope or risk without a decision. For high risk, read [the Hunk handoff](references/hunk-handoff.md) and copy its full agent instructions into the initial prompt with concrete values; a link alone is insufficient. Agents stay in their worktree and leave integration and cleanup to the chief. Parallelize independent tasks.
6. **Communicate and review.** Use pi-intercom as the primary coordination channel. Re-list before reusing a session ID, verify task/cwd, and exclude self. Use `send` for delegation, progress, results, and revised plans; use `ask` for short blocking decisions and `reply` for exact-thread answers. Inspect `pending` and disambiguate multiple asks. Never block the chief waiting for a worker that is itself waiting for the chief. Record returned message IDs: delivery or queueing is not acceptance or completion. On timeout, inspect delivery state and the worker before cancelling, superseding, or authoring a retry; timeout does not cancel work. Herdr owns layout and Hunk; use its read/get/wait for inspection, and prompt only as a deliberate fallback. Preserve user drafts/focus. If risk rises, pause implementation and send the Hunk handoff before further work. Verify the result and whole diff regardless of messages.
7. **Deliver by risk.** Low-risk agents finish verification, open a PR or save a durable artifact, and notify the chief via intercom `send` with the task ID, branch/commit, URL/path, verification results, and remaining gaps; no Hunk review is required. High-risk agents finish verification, open an annotated Hunk split, send “ready for review” to the chief with the task ID and review metadata, and keep their session and worktree open. The chief verifies the annotated diff and presents the decisions to the user; wait for the user’s approval of that reviewed diff before integrating high-risk work. If the implementation changes afterward, refresh the review and obtain renewed approval.
8. **Clean up.** Integrate within the user’s authorization. After confirmed integration or approved abandonment, resolve pending asks and obtain worker acknowledgement that it has stopped editing. Preserve deliverables, stop task processes, use `wt remove <branch>`, and close only the task’s Herdr workspace, never the chief/main workspace or the repository group; do not use `workspace close --group`. If an open operation reused an existing workspace, it is not a resource you created. Verify cleanup through Worktrunk, Herdr, and the intercom roster; cancellation alone does not prove the worker stopped. An open PR is not integrated. Preserve dirty or unmerged work; never force removal or clean up resources you did not create.
